# Работа над Lab Colors

Lab Colors позволяет дизайнеру задать цвета системы через их свойства и связи.
Дизайнер выбирает опорные цвета в исходном окружении, задаёт характер,
материал и отношения между элементами. Ядро подбирает производные цвета вместе
и пересчитывает их при смене окружения. Опоры сохраняются. Хорошее изменение
сокращает число цветов и исключений, которые команде приходится выбирать
вручную для каждой поверхности и темы.

## Кто за что отвечает

- **Дизайн-система задаёт смысл.** У одной опоры может быть несколько применений.
  Вторичный текст на белом листе и на серой карточке может получить близкие,
  но разные оттенки. Два элемента, использующие одну и ту же заливку, сохраняют
  общий физический цвет. Имена ролей, устройство тем и связи между применениями
  задаёт потребитель.
- **Rust Core выбирает цвет.** Идентичность, иерархия, различимость и читаемость
  учитываются в итоговой композиции, включая наложение материалов. Обязательные
  условия должны выполняться вместе. JS/WASM, Swift и Kotlin передают ядру
  декларацию и окружение. Приложение отображает принятый результат.
- **У оценки качества есть область применимости.** Задача Cleanliness — выбирать
  более чистую композицию при сохранении замысла. Для `Cleaner` нужно основание
  считать новое поле чище, для `NotDirtier` — основание для отсутствия ухудшения
  в сопоставимых условиях. Сохраняйте различие между несравнимой парой и полем
  вне области модели. Для переноса с цветовой плашки на градиент или целый экран
  нужны данные о таком поле. Приводите первоисточник, численные границы и контрпримеры.
  [Модель цвета](docs/explanation/color-system.md) · [Возможности и исследования Cleanliness](docs/explanation/color-quality.md).

## Как менять систему

Начните с ситуации, которую можно увидеть или воспроизвести через публичный API.
Если светлая и тёмная темы требуют разных последовательностей поверхностей,
проверьте, может ли потребитель выразить обе общей декларацией. Переименование
роли в этой системе должно сохранять результат подбора.

Закрепляйте гарантию там, где возникает состояние. Например, фон и зависимые
цвета образуют один кадр. Пока новое окружение под контролем приложения,
оно принимает кадр целиком. Когда внешний фон уже изменился, предыдущий
снимок описывает прежний контекст. Выразите это через тип результата и
операцию обновления, чтобы каждому адаптеру хватало одного решения ядра.
[Контракт обновления](docs/contracts/program-transaction.md).

Следуйте именам и стилю соседнего кода. Одна цветовая формула или политика
выбора живёт в одном месте. Комментарий объясняет основание решения. При
изменении API или формата проверьте существующего потребителя и обновите справку.
Документацию пишем по-русски, имена API сохраняем в оригинале.

## Как проверить изменение

Выбирайте проверку по свойству, которое могло сломаться. Для численной границы
подойдёт независимый эталон. Для адаптации покажите один и тот же интерфейс
до и после смены подложки, включая соседний элемент, который должен сохранить
свой цвет. Для локального пересчёта измерьте задержку до пригодного кадра и
память на одинаковой нагрузке. Изменения поставки проверяйте установкой
библиотеки во внешнем проекте.

В pull request опишите исходную проблему, что изменилось для потребителя и
как это проверить. [С чего начать](README.md) ·
[Проверки адаптации](docs/how-to/test-adaptive-contract.md) ·
[Измерение производительности](docs/how-to/benchmark-program.md).
