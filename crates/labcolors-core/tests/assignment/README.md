# Проверка назначения цветов

Это исполняемый эксперимент внутри integration tests. Он не добавляет публичный
API, путь эмиссии, новую модель цвета или runtime-зависимости Core. Его входы —
математически заданные области sRGB8, авторские опоры, направленные ограничения
контраста и отношения яркости. Клиент не перечисляет готовые варианты цветов.

Численные области и Q55-значения здесь — внутренние математические входы пробы.
Они не задают эргономику будущего публичного декларативного API.

## Метод проверки

Исполнение последовательное, в существующем release-профиле workspace.
Компиляция и подготовка входов не входят в время вызова поиска. Первый вызов
показывается отдельно от повторного; два измерения не описывают p95/p99.

Сравниваются полный перебор и тот же перебор с сокращением целых отрезков по
доказанным границам яркости. Полный независимый oracle посещает весь sRGB8-куб
для одноцелевых случаев; для связанных целей полностью посещает заданные
отрезки серой оси. Эти конечные области задаются границами, а не списками RGB.
В raw output сохраняются вход, итог, число посещённых/проверенных состояний,
время обоих поисков и независимого oracle. `examined` считает полные назначения,
включая отдельную проверку опор; бюджет ограничивает это число, не время или
число interval checks. `pruned_values` считает пропущенные значения текущей
цели; в многомерном поиске это не число всех пропущенных полных назначений.

Hard predicates отделены от предпочтения. Контраст оценивается на финальных
байтах действующим Q55 evaluator. Oracle независимо воспроизводит integer
arithmetic над тем же нормативным, отдельно проверенным Q55 artifact; это общая
предпосылка данных, а не независимая колориметрическая модель. Его Oklab и
поиск записаны отдельно по формулам Ottosson 2021-01-25. Предпочтение —
лексикографический вектор квадратов ΔEOK в объявленном порядке целей,
затем байтовый порядок для равных значений. Заявляется только совпадение
полученных решений на проверенных случаях; близкие floating-point ties не
превращаются в доказательство универсального вещественного минимума.

Ограничения и допуски каждого случая являются синтетической политикой
потребителя, а не калибровкой конкретной дизайн-системы или общим эстетическим
default. Допуск ΔEOK равен 0.3 в серых случаях и 0.1 в полнокубовых; gap `2^50`
при шкале Q55 означает 1/32 относительной яркости. Допустимая
полная авторская опора сохраняется побитово: её нулевое отклонение минимально.
При конфликте другой цели поиск также должен сохранять допустимую сильную
опору первой назначаемой цели. Бюджет исчерпан — `Unresolved`; `Unsatisfied`
возможен только после полного исчерпания заданной области.

Обязательные случаи: светлый фиксированный цвет/назначаемая насыщенная заливка;
сильный основной/назначаемый вторичный цвет; противоположная полярность и обратная
двухцелевая иерархия другого потребителя; связанная пара, нарушаемая независимым
последовательным ремонтом;
граница квантования; пустая область; исчерпанный бюджет; смена наблюдаемого цвета;
переименование opaque ID при уникальном предпочтительном решении.

Команды:

```powershell
cargo test -p labcolors-core --test assignment_probe
cargo test -p labcolors-core --release --test assignment_probe -- --ignored --nocapture --test-threads=1
cargo clippy -p labcolors-core --test assignment_probe -- -D warnings
```

Порог задержки для нового назначения здесь не установлен. Измерения не дают
production-performance PASS. Dev-only эксперимент не измеряет будущий вклад
назначения в shipping WASM и не заявляет нулевую стоимость.
Пространственные материалы, runtime-инвалидация и нативные bindings этим
экспериментом не квалифицируются.

Основания: [WCAG 2.2](https://www.w3.org/TR/2024/REC-WCAG22-20241212/),
[Oklab](https://bottosson.github.io/posts/oklab/),
[CSS Color 4, ΔEOK](https://www.w3.org/TR/css-color-4/#color-difference-OK).
