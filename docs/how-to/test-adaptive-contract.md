# Проверять адаптивный цветовой контракт

Цель проверки — убедиться, что результат определяется декларацией клиента,
контекстом и общими законами ядра. Замена дизайн-системы меняет декларацию,
а не добавляет в Core названия ролей, палитру или специальную ветвь.

Исходные RGB/OKLCH и брендовые anchors законны: клиенту нужен исходный материал.
Проверка адаптивности не закрепляет один итоговый HEX для токена. Она проверяет,
какие результаты допустимы и какой из них выбирает объявленная политика.

## Начните с публичного потребителя

[Исполняемый контракт](../../packages/colors/test/program-adaptive-contract.test.mjs)
импортирует только публичные exports пакета. Он выполняется обычным
`npm test` в `packages/colors` после сборки WASM. Проверка выпуска копирует тот же
файл во внешний проект с установленным tarball; этот путь выполняется также
на минимальной поддерживаемой версии Node.

Для адресного запуска на CI-исполнителе с уже собранным пакетом:

```sh
cd packages/colors
node --test test/program-adaptive-contract.test.mjs test/program-adaptive-mutations.test.mjs
```

Не заменяйте этот путь проверкой одного внутреннего helper или mock решателя.
Тесты запускаются на CI-исполнителях, не на операторском sandbox.

## Выберите свойство и неверную реализацию

| Свойство | Как проверить | Что проверка должна обнаружить |
|---|---|---|
| Намерение управляет результатом | Сменить preference при нескольких допустимых состояниях | Выбор самого светлого цвета или максимального контраста вместо решения клиента |
| Дизайн-система заменяема | Подставить другие цветные каналы, прозрачности и opaque IDs | Встроенную палитру, ветвление по ID, потерю канала или прозрачности |
| Граф задаёт смысл | Переставить unordered declarations и читать outputs по slot | Зависимость от позиции в массиве или численного порядка ID |
| Hard constraints независимы | Отвергать предпочтительные состояния, нарушающие хотя бы одно требование | Компенсацию нарушения другим критерием, пропуск ограничения |
| Выбор совместный | Перебрать полные tuple нескольких связанных targets | Независимый подбор локальных значений или проверку одного count вместо полного множества |
| Учитывается каждый контекст | Изменить, переставить и повторить фоны | Оценку только первого фона, повторное использование старого решения |
| Диагностика не меняет политику | Добавить противоречащее report-only ограничение | Необъявленный veto |
| Невозможность остаётся явной | Проверить failed, отзыв attachment и последующее восстановление | Правдоподобный fallback или публикацию старого решения как нового |

Переименование ключей состояний внутри одного tie group — отдельный случай:
их canonical order участвует в объявленном tie-break. Не требуйте инвариантности
при изменении семантики. В новом conformance-наборе ранги одноэлементные;
проверки tied states остаются в существующих selection-тестах.

Каждому отказу нужен законный соседний успех. Дополнительно проверяйте,
что контекст действительно меняет выбранные значения, несколько допустимых
состояний достигаются и меняющиеся предпочтения остаются действенными.
Система, которая всегда отказывает или всегда возвращает один цвет, не проходит.

## Получите ожидаемый результат независимо

В conformance-наборе используются два небольших исчерпывающих эталона:

1. **Композиция и совместный выбор.** Для объявленной прозрачности `q/4`
   source-over вычисляется целочисленно. Округление half-up происходит после
   каждого occurrence в поддерживаемой encoded-sRGB8 модели. Затем отдельный
   перебор оставляет tuple, удовлетворяющие всем hard constraints на всех
   фонах, и берёт первое по порядку клиента. Exact-visible значения здесь —
   построенные требования тестового клиента, а не универсальные цвета ролей.
   Отдельный случай допускает две диагональные пары и отвергает перекрёстные:
   такое множество нельзя получить независимым выбором каждого target.
2. **Контраст без палитрового рецепта.** Перебираются все вершины sRGB-куба
   и циклические порядки предпочтения. В этих точках transfer function даёт
   точно 0 или 1: relative luminance и сравнение контраста сводятся к целым
   числам. Пороги UI и обычного текста взяты из
   [WCAG 2.2 от 12 декабря 2024](https://www.w3.org/TR/2024/REC-WCAG22-20241212/).
   Они передаются как разные явные критерии.

Первый эталон проверяет дискретную модель Program; он не удостоверяет
неизвестный браузерный renderer. Второй проверяет выбор по WCAG в указанном
домене, а не заменяет численные проверки полного sRGB8-пространства.
Ни один из них не доказывает универсальную гармонию, предпочтение или
человеческое восприятие цвета.

Не вычисляйте expected через проверяемый solver. При расширении домена
сначала найдите независимый эталон или обоснованное преобразование.
Например, перестановка RGB-каналов допустима для exact-composition отношений,
но не для WCAG: у каналов разные веса.

## Проверьте, что тест чувствителен к ошибке

[Адресные мутации](../../packages/colors/test/program-adaptive-mutations.test.mjs)
запускают один и тот же публичный witness на здоровой копии пакета и на трёх
изолированных изменениях encoder: обратный preference, потерянная opacity,
report-only как hard constraint.

Здоровая копия обязана пройти. Для мутанта засчитывается только assertion
именно этого witness; ошибка импорта, синтаксиса, зависание или отсутствие WASM
не считаются найденным предметным дефектом. Временные копии удаляются после
каждого запуска. Это узкая проверка чувствительности, не общий mutation score.

## Не переносите локальный рецепт в ядро

Число должно иметь владельца и основание: versioned standard, точный вывод,
опубликованную модель с областью применимости, явную политику клиента либо
экспериментальную гипотезу вне defaults. Переименование литерала в константу
само по себе не создаёт такого основания. Epsilon не ослабляет hard requirement.

Изменение новой брендовой палитры, языка ролей или предпочтений должно оставаться
в декларации и адаптере этой дизайн-системы. Новая общая возможность принадлежит
Program/constraint/output-контракту и получает проверку с другими клиентскими
входами. Известные удалённые recipe-пути дополнительно охраняются source guards;
поиск запрещённых слов не доказывает отсутствие нового рецепта под другим именем.

Текущий V2 проверяет конечные связанные targets и полный объявленный продукт
состояний в пределах своих budgets. Не выдавайте этот набор тестов за поддержку
произвольного непрерывного поиска, всех топологий или неограниченного размера.
