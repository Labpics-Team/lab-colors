# Измерить компиляцию и обновление цветов

Соберите `@labpics/colors` штатной командой из `packages/colors/package.json`.
Из корня репозитория запустите:

```sh
node packages/colors/bench/program.mjs packages/colors repeated 8 7
```

Официальная сборка использует Cargo `opt-level = 2`, LTO и закреплённый
Binaryen `-Oz`: настройки исполнения и конечный размер проверяются вместе.
При изменении профиля сравнивайте оба артефакта одной парной серией; фиксируйте
raw/gzip размер, холодный цикл и пиковую память процесса рядом со скоростью.
Рецепт и инструментальная цепочка заданы в
[`package-worker.yml`](../../.github/workflows/package-worker.yml).

Аргументы: каталог собранного пакета, рисунок графа, число цветовых узлов,
число сохраняемых измерений, необязательный способ чтения outputs
(`auto`, `table` или `getters`), число циклов прогрева и число обновлений
в каждом цикле. По умолчанию сохраняются 7 измерений после одного начального
цикла, каждый цикл содержит 64 обновления. Число циклов прогрева включает
первый холодный цикл и должно быть положительным целым. Число обновлений
должно быть положительным и кратным четырём, чтобы каждый цикл завершал
отказ и восстановление. `repeated` повторяет одинаковые цвета,
`distinct` задаёт разные, `shared` использует общий источник,
`grouped` распределяет узлы между четырьмя цветами. `sparse` задаёт независимую
подложку каждой ветви и меняет только одну из них за обновление, включая отказ
и восстановление при неизменном непрозрачном цвете. `ring` соединяет одинаковые
цветовые узлы кольцом обязательных точных отношений между соседними целевыми узлами;
для него допустимо от 3 до 2048 узлов: на каждый нужны два жёстких ограничения.
Кольцо сохраняет прежние ожидаемые цвета
и проверяет путь, в котором независимых взаимозаменяемых компонент нет.
`complete` связывает каждый узел со всеми остальными, `bipartite` — с каждым
узлом противоположной половины. Эти плотные диагностические графы сохраняют
одинаковые цвета; для них допустимы 2–32 узла, у `bipartite` число чётное.

JSON содержит исходные времена в миллисекундах, версию Node.js,
идентификатор исходников ядра, размер и SHA-256 WASM. `cold` сохраняет первый
цикл, `warmupSamples` — остальные циклы до выбранной границы, а
`samplesAfterWarmup` — все последующие измерения. Ни один цикл не удаляется.
Поля `warmups` и `frames` фиксируют параметры, `stabilization: "unverified"`
указывает, что сам скрипт не проверяет установившийся режим движка.
Каждый цикл включает компиляцию, обновления фона,
чтение цветов, отказ при недостаточном контрасте, восстановление и освобождение
ресурсов. Время обновления включает чтение и проверку результатов.

По умолчанию `auto` читает все outputs через `copyOutputTable()`, если
собранный пакет предоставляет этот метод. Базовый пакет без метода использует
поштучные `outputSlot`/`outputRgb`/`outputOpacity`. В обоих случаях один oracle
проверяет точное равенство каждого slot, каждого RGB-канала и opacity;
контрольная сумма и последовательность lifecycle одинаковы. Поле `readout`
в JSON фиксирует фактический путь. `table` требует массового API, `getters`
позволяет измерить стоимость поштучного чтения на том же артефакте:

```sh
node packages/colors/bench/program.mjs packages/colors distinct 1024 7 table
node packages/colors/bench/program.mjs packages/colors distinct 1024 7 getters
```

Для сравнения подготовьте оба пакета и чередуйте запуски с одинаковыми
аргументами на одной машине. Предварительно изучите полные временные ряды
обеих версий: компиляция WASM и оптимизация JavaScript могут продолжаться
после первого цикла. Выберите общую границу прогрева до итогового сравнения
и проверьте её на всех сценариях; само число пропущенных циклов не доказывает
стабилизацию. Холодный путь и нерегулярные паузы сохраняйте отдельно.

Единица независимого наблюдения — новый процесс. Сначала вычисляйте медиану
измерений внутри каждого процесса, затем отношения соседних пар и их разброс;
внутренние циклы одного процесса не увеличивают число независимых повторов.
Сопоставляйте медиану и хвост распределения по каждому рисунку графа;
завершившийся тайм-аутом запуск сохраняйте как
незавершённый. Начальную загрузку и обновления сравнивайте отдельно от компиляции.
`maxRssKiB` отражает максимум памяти всего процесса, включая движок JavaScript.

Регрессия перебора повторяющихся компонент проверяется в тестах ядра числом
посещённых листьев поиска. Скорость конкретной машины в условие этого теста
не входит.

## Сравнить PR с его базой в CI

Добавьте PR метку `performance` перед следующим push. Само добавление метки
не запускает CI. Измерение выполнится при следующем обычном запуске CI для PR,
например после отправки новых коммитов. Штатное задание пакета
соберёт текущий снимок исходников и точный `base.sha` одинаковым набором
инструментов и `build_runtime`, затем запустит один и тот же сценарий измерений
через публичный API пакета на одной машине.
Остальные проверки пакета сохраняются.

Это явно запрошенная PR-диагностика: `merge_group` не содержит меток PR и не
запускает её автоматически. Парные CLI-проверки и обязательные проверки пакета
работают в очереди независимо от этой метки; их исходники описаны в
[контракте CI](../contracts/ci-evidence.md).

Во время работы CI в `$RUNNER_TEMP/program-performance` формируются идентификаторы базы,
проверенного снимка исходников и вершины PR, версии инструментов, SHA-256 обоих WASM,
исходные наблюдения и `summary.json`. После завершения задания они не сохраняются
в GitHub Actions как артефакт. Для четырёх основных рисунков графа
измеряются размеры 8, 64, 256, 1024, 4096. Порядок запусков каждого сценария —
база, изменение, изменение, база.
Короткий протокол по умолчанию выполняет один начальный цикл и три последующих
по 64 обновления. В metadata и summary он обозначен как `diagnostic` с
непроверенной стабилизацией. Он помогает выбрать случаи для подробного
исследования; утверждение об установившейся скорости требует отдельной
квалификации общего прогрева и новых независимых процессов.

Для каждого случая отдельно сравниваются компиляция, сумма 64 обновлений с
чтением и проверкой выходов, полный цикл после выбранной границы и холодный цикл.
Сводка сохраняет медианы каждого процесса и оба парных отношения AB/BA.
Итоговое отношение — медиана этих двух отношений; общая медиана всех внутренних
циклов разных процессов не используется. Параметры ручного запуска
`--samples`, `--warmups` и `--frames` задают один протокол для обеих версий;
их увеличение учитывайте в общем лимите времени.
Один процесс ограничен 180 секундами, вся матрица — 900 секундами.
`timeout` и `budget-exhausted` означают незавершённое измерение; они остаются
в отчёте и не участвуют в отношении скоростей. Неудачная проверка результатов
публичного API завершает сравнение ошибкой. Отношение вычисляется только после
завершения обоих повторов обеих версий с совпавшими контрольными суммами.

Матрица также включает `sparse` размером 8, 64, 256, 1024, 4096 и связный
симметричный `ring` размером 8, 64, 256, 1024 и 2048. Сравнивайте его отдельно: это проверка времени и результатов
общего пути, а равенство канонических байтов защищают дифференциальные тесты ядра.
Плотные `complete/8` и `bipartite/16` отдельно проверяют стоимость поиска
симметрий: ускорение волн уточнения на кольце не определяет их результат.

После сравнения CI отдельно снимает CPU-профили обеих версий для `repeated/1024`,
`distinct/1024` и `ring/256`. Используется тот же сценарий со всеми проверками
результатов. Эти запуски не входят в `summary.json` и отношения скоростей:
профилировщик влияет на время исполнения. Профиль охватывает весь процесс,
включая загрузку и прогрев; откройте файл `.cpuprofile` в инструментах разработчика.
В каталоге `profiles` сохранены профили, исходные выводы процессов, контрольные
суммы и лимиты времени. Тайм-аут профилирования остаётся незавершённым наблюдением.
При ручном запуске скрипта сравнения этот этап включается аргументом `--profile`.

## Измерить выбор цвета при смене контекста

Основная матрица использует фиксированные цвета. Отдельный сценарий проверяет
конечный выбор из трёх цветов с объявленным порядком предпочтения:

```sh
node packages/colors/bench/selection.mjs packages/colors 64 7
```

Аргументы — каталог пакета, число мест применения цвета, число сохраняемых
измерений, необязательные число циклов прогрева и число обновлений на цикл.
Для последних параметров действуют те же значения по умолчанию и ограничения, что и у
`program.mjs`. Каждый цикл компилирует Program V2 и по умолчанию выполняет
64 обновления: один светлый фон,
два фона с более строгим пересечением ограничений, несовместимые светлый и
чёрный фоны, затем восстановление на чёрном. Успешные обновления должны выбрать
соответственно RGB `[80, 80, 80]`, `[0, 0, 0]` и `[180, 180, 180]`; конфликт
должен завершиться состоянием `failed`. Проверки всех выходов и освобождение
ресурсов входят во время полного цикла.

Для обеих версий используйте этот же сценарий и чередующийся порядок запусков.
Он отдельно сохраняет холодный цикл, компиляцию и обновления, проверяет каждый
канал и opacity, а также контрольную сумму. Его результат относится к выбору
одного общего цвета для нескольких мест применения; число независимых целевых
цветов и размер пространства совместного выбора измеряйте отдельно.

## Измерить локальную адаптацию независимых композиций

`computed-locality.mjs` проходит публичный путь `colors({ reference })` →
`compile()` → `resolve()`. Каждая композиция содержит два вычисляемых текста
на своей наблюдаемой подложке, контраст обычного текста и сохранение исходной
тональной иерархии. Общие роли получают независимые местные применения;
домен нейтральных sRGB8 позволяет требовать завершённую оптимизацию.

```sh
node packages/colors/bench/computed-locality.mjs packages/colors 1 7 1 16
node packages/colors/bench/computed-locality.mjs packages/colors 32 7 1 16
node packages/colors/bench/computed-locality.mjs packages/colors 32 7 1 16 shared-input
```

Аргументы — каталог собранного пакета, число композиций (1–256), число
измерений, циклов прогрева, обновлений и рисунок входов. Начальное разрешение
адаптирует все композиции с белого исходного окружения к чёрному. Каждая
четвёрка обновлений меняет одну подложку на белую, повторяет тот же контекст,
возвращает чёрную и повторяет его. Следующая четвёрка выбирает соседнюю
подложку. В `shared-input` одна наблюдаемая подложка используется всеми
композициями: её изменение действительно затрагивает каждый результат.

`firstUsefulMs` включает декларацию, компиляцию и первое пригодное разрешение;
`firstResolveMs` выделяет первое разрешение. Загрузка модуля и WASM указаны
отдельно. `byPhaseMs` разделяет локальное изменение, неизменный контекст и
возврат. Времена включают чтение всех outputs и проверки: `ready`, `exact`,
точные RGB/opacity, свежие reference-данные, независимый расчёт WCAG и
тонального отношения. Белая подложка даёт нейтральные уровни 68 и 102,
чёрная — 177 и 134; эти ожидаемые физические результаты одинаковы при любом
числе независимых композиций. `checksum` — SHA-256 последовательности состояний,
полноты оптимизации и всех физических outputs. Сравнение версий требует его
совпадения. Проверка времени не задаёт порога успешности. Сравниваемые пакеты
должны быть собраны одной цепочкой и иметь одинаковую доступность producer
identity. Локальная сборка без неё сообщает `producer: null` и причину в
`producerIdentityError`; это диагностическое измерение, не проверка выпуска.

Параметры прогрева и порядок независимых процессов выбирайте так же, как для
основной матрицы. `independent` и `shared-input` сравнивайте отдельно: стоимость
передачи полного контекста, чтения и проверки всех outputs растёт с их числом
даже при повторном поиске только одной композиции.

Для отдельной, не входящей во времена пробы памяти добавьте `--expose-gc`:

```sh
node --expose-gc packages/colors/bench/computed-locality.mjs packages/colors 32 7 1 16
```

`retainedMemoryBytes` сохраняет `process.memoryUsage()` после явной сборки
мусора до пробы, при живых Program и последнем frame, затем после `dispose()`
и удаления ссылок. Поля описаны в [документации Node.js](https://nodejs.org/api/process.html#processmemoryusage).
Это память процесса, включая ёмкость WASM allocator; она не равна сумме живых
объектов библиотеки и не обязана возвращаться ОС после освобождения. Проба
повторяет тот же проверяемый сценарий после временных измерений. Без
`--expose-gc` поле равно `null`; обычные память в конце и максимум RSS остаются.

## Выделения памяти

Счётчик тестов отдельно считает выделения (`alloc` и `alloc_zeroed`),
реаллокации и освобождения,
наблюдая текущий поток через настоящий системный allocator. Проверка
`program_allocation_tests` охватывает весь Rust-вызов update, включая
проверку заимствованной матрицы и создание независимого результата:

```sh
cargo test -p labcolors-core --lib program_allocation_tests --locked
cargo test -p labcolors-ffi --test program_runtime observed_native_call_has_no_per_scenario_allocations --locked
```

В первой команде прогрев выполняется до измерения и явно охватывает
используемые рабочие слоты. Проверяются прямое обновление, повтор ревизии,
attachment, Ready → Failed → восстановление и Unknown; старые снимки
продолжают читаться. Размеры входов и необходимые ёмкости после прогрева
не увеличиваются. В этих условиях один output хранится inline без heap;
для нескольких outputs создаётся один независимый буфер без реаллокаций.
Временных массивов сценариев нет.

Native-проверка измеряет публичный `ProgramRuntime::update_observed`
с одним output и заранее созданными входными `Vec`.
Цвет хранится в самом объекте результата: метод выделяет ровно один `Arc`,
без реаллокаций. Отдельная проба включает создание двух входных векторов и
ожидает три аллокации. Число сценариев не добавляет аллокаций на каждую строку.
Отдельный native attachment создаёт ещё один RGB-буфер sink-команды
до вызова callback. Его проверка учитывает этот буфер отдельно от `Arc`
результата и от возможных расходов пользовательского callback.
Это не измерение сгенерированного Swift/Kotlin marshalling и не число
объектов JavaScript.

Для полного lifecycle измеряйте compile, instantiate/attach, холодные
обновления, рост входа и уничтожение отдельно от устойчивого режима.
Один успешный update не прогревает автоматически все слоты. Новые размеры,
новые физические сочетания и более сложные переходы могут потребовать
дополнительной рабочей памяти. Не переносите аллокации за начало таймера,
называя результат стоимостью всего вызова, и не исключайте ошибочные пробы.

Счётчики памяти не заменяют замеры времени, удерживаемой памяти и размера
пакета. Они защищают конкретную форму работы от повторного создания
временных входов; скорость и результаты проверяются независимо.
