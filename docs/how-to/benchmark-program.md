# Измерить компиляцию и обновление цветов

Соберите `@labpics/colors` штатной командой из `packages/colors/package.json`.
Из корня репозитория запустите:

```sh
node packages/colors/bench/program.mjs packages/colors repeated 8 7
```

Аргументы: каталог собранного пакета, рисунок графа, число цветовых узлов,
число измерений после прогрева. `repeated` повторяет одинаковые цвета,
`distinct` задаёт разные, `shared` использует общий источник,
`grouped` распределяет узлы между четырьмя цветами. `ring` соединяет одинаковые
цветовые узлы кольцом обязательных точных отношений между соседними целевыми узлами;
для него допустимо от 3 до 2048 узлов: на каждый нужны два жёстких ограничения.
Кольцо сохраняет прежние ожидаемые цвета
и проверяет путь, в котором независимых взаимозаменяемых компонент нет.

JSON содержит исходные времена в миллисекундах, версию Node.js,
идентификатор исходников ядра, размер и SHA-256 WASM. Первое измерение
сохранено отдельно. Каждый цикл включает компиляцию, обновления фона,
чтение цветов, отказ при недостаточном контрасте, восстановление и освобождение
ресурсов. `compileMs` начинается после построения wire-декларации.
`updatesMs` содержит времена 64 отдельных обновлений с чтением и проверкой
результатов; `updatesMedianMs` в сводке сравнивает медиану их суммы за цикл.
`cycleMs` включает компиляцию, обновления и освобождение ресурсов.
Эти величины сравниваются отдельно: ускорение компиляции не переносится на runtime.

Для сравнения подготовьте оба пакета и чередуйте запуски с одинаковыми
аргументами на одной машине. Сопоставляйте медиану и хвост распределения
по каждому рисунку графа; завершившийся тайм-аутом запуск сохраняйте как
незавершённый. Начальную загрузку и обновления сравнивайте отдельно от компиляции.
`maxRssKiB` отражает максимум памяти всего процесса, включая движок JavaScript.

Регрессия перебора повторяющихся компонент проверяется в тестах ядра числом
посещённых листьев поиска. Скорость конкретной машины в условие этого теста
не входит.

## Сравнить PR с его базой в CI

Добавьте PR метку `performance` перед следующим push. Само добавление метки
не запускает CI. Измерение выполнится при следующем обычном запуске CI для PR,
например после отправки новых коммитов. Штатное задание пакета
соберёт текущий снимок исходников и точный `base.sha` одинаковым набором
инструментов и `build_runtime`, затем запустит один и тот же сценарий измерений
через публичный API пакета на одной машине.
Остальные проверки пакета сохраняются.

Во время работы CI в `$RUNNER_TEMP/program-performance` формируются идентификаторы базы,
проверенного снимка исходников и вершины PR, версии инструментов, SHA-256 обоих WASM,
исходные наблюдения и `summary.json`. Поле `runtimePayload` также содержит
размеры и SHA-256 собранных WASM, `pkg/labcolors.js`, JavaScript snippets,
`index.js` и модулей `program-wire`, а также их суммарный размер. Это проверяет совместную стоимость переноса кода
между WASM, JavaScript и построителем декларации.
Метаданные, холодные и прогретые отсчёты,
статусы и сводка также выводятся в журнал CI. После завершения задания временные
файлы не сохраняются в GitHub Actions как артефакт. Для четырёх основных рисунков графа
измеряются размеры 8, 64, 256, 1024, 4096. Порядок запусков каждого сценария —
база, изменение, изменение, база.
Каждый процесс сохраняет холодный цикл и три цикла после прогрева.

Один процесс ограничен 180 секундами, вся матрица — 900 секундами.
`timeout` и `budget-exhausted` означают незавершённое измерение; они остаются
в отчёте и завершают сравнение с ошибкой. Тем же отказом заканчивается
запуск не той сборки, неполный набор повторов или несовпадение результатов
публичного API. Холодный цикл сравнивается отдельно от прогретых. Отношение вычисляется только после
завершения обоих повторов обеих версий с совпавшими контрольными суммами.

Для контроля связного симметричного графа матрица также включает `ring`
размером 8, 64, 256, 1024 и 2048. Два последних размера выполняются после всех
исходных сценариев, чтобы незавершённое измерение большого связного графа не
вытесняло проверки остальных форм. Сравнивайте его отдельно: это проверка времени и результатов
общего пути, а равенство канонических байтов защищают дифференциальные тесты ядра.

После сравнения CI отдельно снимает CPU-профили обеих версий для `repeated/1024`,
`distinct/1024`, `ring/256` и `ring/2048`. Используется тот же сценарий со всеми проверками
результатов. Эти запуски не входят в `summary.json` и отношения скоростей:
профилировщик влияет на время исполнения. Профиль охватывает весь процесс,
включая загрузку и прогрев. Журнал CI содержит сводку по фактическим интервалам
`samples/timeDeltas`: полное измеренное время, хвост без отсчёта и наиболее
затратные узлы по собственному времени и времени с потомками. Если V8 вернул отсчёты не по времени, анализатор сначала восстанавливает метки
времени из дельт, затем сортирует их вместе с номерами кадров, как в
[Chrome DevTools](https://chromium.googlesource.com/devtools/devtools-frontend/+/9a696c4e723caa3c7e1f78886da353f1f06a79b0/front_end/core/sdk/CPUProfileDataModel.ts).
Число таких событий выводится отдельно. Границы записи проверяются до сортировки;
интервалы не отбрасываются и не заменяются нулями. Времена с потомками
у разных узлов пересекаются; складывать их нельзя. Эта сводка помогает выбрать
следующее изменение, но не входит в измерение ускорения.
Временный каталог `profiles` содержит полные `.cpuprofile`, исходные выводы
процессов, контрольные суммы и лимиты. При локальном запуске на CI-исполнителе
полный профиль можно открыть в инструментах разработчика. Тайм-аут запрошенного профиля сохраняется в отчёте и завершает запуск с ошибкой.
При ручном запуске скрипта сравнения этот этап включается аргументом `--profile`.

После завершения того же сценария диагностическая оболочка читает уже созданный
экземпляр WASM и сохраняет `memory.buffer.byteLength`, `process.memoryUsage()`
и статистику heap/code V8. Хеш оболочки указан в метаданных профилирования.
Линейная память этого экземпляра не уменьшается, поэтому её конечная ёмкость
показывает достигнутый предел выделенных страниц. Статистика JavaScript относится
к моменту после сценария, а не к максимуму живых объектов. Она дополняет исходный
`maxRssKiB` всего процесса; эти показатели не подменяют друг друга. Оболочка
не запускается в обычных процессах измерения скорости и не вызывает сборку мусора.

## Проверки общей сложности и совместимости

Регрессионные тесты уточнения графа сравнивают упорядоченные множества вершин
каждой клетки после каждого синхронного раунда с замороженной полной реализацией.
Порядок равных вершин внутри клетки не является частью декларации; точные байты V9
дополнительно сравниваются с полным поиском, который использует прежний алгоритм уточнения.
Так проверяющий путь остаётся независимым от новой оптимизации.

Счётчики существуют только в тестовой сборке и увеличиваются при фактическом
построении сигнатуры и чтении дуги. На направленных путях тест ограничивает эту
работу размером графа, а на связанных циклах отдельно ограничивает повторное
построение одной орбиты. Проверка опирается на выполненную работу, поэтому её
результат не зависит от скорости CI-исполнителя.

Построение списка смежности проверяется отдельно от уточнения разбиения.
Тест задаёт ожидаемые строки вручную: проверяет направление, тип и кратность
дуг, обе дуги петли и пустой граф. Эталон не использует построитель графа,
общий для двух алгоритмов канонизации. Счётчик выделений памяти показывает,
как меняется их число при росте графа. Тест также сверяет все заявленные дуги.

Число выделений памяти и ёмкость оставшихся буферов проверяются отдельно.
Тест увеличивает одновременно число исходных одноэлементных клеток и число
клеток, которые впервые становятся одноэлементными при разбиении. Каждая такая
клетка хранит вершину непосредственно: для неё не нужен отдельный буфер.
Число выделений не должно расти с числом этих вершин. Отдельная проверка
грубого равновесного разбиения увеличивает число вершин внутри тех же клеток:
ёмкость внешнего контейнера должна зависеть от числа клеток. Обе проверки также
сопоставляют полное упорядоченное разбиение с прежней реализацией. Они не заменяют
измерение RSS и не доказывают постоянную память всего поиска: сохранённые ветви
и автоморфизмы по-прежнему могут требовать квадратичную память.

Выбор затронутых вершин выводится из разбиения и типизированных дуг общего графа.
Для ускорения не нужны правила конкретного бренда, роли интерфейса или цвета.
Полученные отношения скоростей относятся к указанным размерам и формам графа:
отдельный выигрыш компилятора нельзя объявлять ускорением всех обновлений.
