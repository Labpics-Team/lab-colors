# Контракт платформенных адаптеров

Математика, граф Program, ревизии наблюдений, выбор результата и ошибки
принадлежат Rust Core. `program_wire` является общей границей исполнения.
WASM и UniFFI вызывают её, не создавая отдельного решателя или урезанного
нативного движка. Изменение формулы не требует ручного переноса в другой язык.

## Три независимые ответственности

Языковая граница переводит типы, ошибки и владение ресурсами. Swift и Kotlin
генерируются из одного UniFFI-контракта. Новый поддерживаемый UniFFI язык
не требует ещё одной реализации цветовых операций.
Языковой builder только кодирует канонический wire и проверяется независимыми
байтовыми примерами. Предварительно вычисленные токены не заменяют runtime.

Платформенная поставка владеет ABI, архитектурами, минимальными версиями ОС,
упаковкой и установкой. Эти сведения не входят в Core и не становятся
параметрами цветового графа. Возможность скомпилировать Rust для платформы
не равна поддержке готового SDK.

Интеграция с отображением получает наблюдения и атомарно применяет результат
через host-порт. DOM, SwiftUI, UIKit и другие UI-системы остаются внешними
потребителями. Адаптер UI не пересчитывает цвет и не объявляет неизвестный
renderer подтверждённым. Приложение сохраняет владение внешним scope и его отзывом.

## Массовое чтение outputs

`ProgramSnapshot` и `ProgramAttachedSnapshot` предоставляют
`copy_output_table()` в Rust, `copyOutputTable()` в Swift и Kotlin.
Один вызов возвращает независимую плоскую таблицу из пяти значений на output:
`[slot, red, green, blue, opacity]`. Строка `i` совпадает с поштучными геттерами
output с индексом `i`; эти геттеры сохраняются для отдельных значений.

| Граница | Тип успешного результата |
| --- | --- |
| Rust UniFFI | `Vec<f64>` |
| Swift | `[Double]` |
| Kotlin | `List<Double>` |

Целый u32 slot и каналы sRGB8 представимы в f64 точно. Opacity переносится
из снимка без изменения точности. Таблица принадлежит вызывающему коду,
сохраняется после обновления или освобождения native-владельца и снимка;
изменение своей копии не меняет другие результаты. Снимок без outputs
возвращает пустую таблицу.

Чтение не меняет lifecycle: `ready` относится к текущему контексту и его
заявленной модели. Для поля `field_assessment()` сообщает `rendering: "unknown"`
и не удостоверяет точность фактического renderer-а. Legacy V1/V2 могут сохранять
предыдущие outputs в `failed` и `stale`
для просмотра; computed V3 возвращает outputs только для текущего `ready`.
Переполнение размера таблицы или отказ её выделения на Rust-стороне возвращает
`LabColorsError.Refused` с `code: "program_resource_exhausted"` и
`operation: "copyOutputTable"`. Отказ не меняет снимок.

## Computed snapshots и совместное обновление

`ProgramSnapshot` отдаёт `snapshot_version`, `revision`, `state`, `reason` и
`optimality` из Core. Для V3 версия снимка равна 2; `optimality` имеет значения
`exact` или `unfinished` только у уже допустимого `ready`. `reason` равен
`limit` у `incomplete`, иначе отсутствует.

`assessment_report()` возвращает `Option<ProgramAssessmentReport>` с identity,
ревизией, provenance сценариев, типизированными оценками ограничений и сводкой
`cleanliness`. Узкий `cleanliness_assessment()` получает ту же сохранённую сводку
без копирования всех клеток. Отсутствие текущего `ready` возвращает `None`;
отсутствие объявленной модели в готовом кадре имеет отдельный статус `NotAssessed`.
Соответствие `nominal-srgb8-v2` описывает только объявленные конечные точки
и не означает `Cleaner` / `NotDirtier` всей композиции.

`nominalSrgb8Visible` в Swift и Kotlin кодирует то же ограничение конечного
видимого цвета, что и JS builder. Прежний `declaredSrgb8CleanSet` сохраняет
свой отдельный контракт причинного вклада. Оба варианта оценивает Rust Core.

`diagnostics()` возвращает `Option<ProgramDiagnostics>` с search budget,
числом посещений и [witness конкретного attempt](../reference/program-diagnostics.md).
Эти owned-records копируются с проверкой выделения памяти. Изменение своей копии
не меняет снимок. `ProgramRgb8` передаёт три u8-канала без отдельной аллокации
на каждый цвет; численные поля оценок переносятся без повторного вычисления.

`update_observed_with` предоставляет тот же
[атомарный host-путь](program-transaction.md#native--uniffi), что и WASM.
Он подготавливает снимок, вызывает `ProgramUpdateHost.accept`, затем принимает
переход только при `true`. Снимок и runtime остаются разными ARC-владельцами;
runtime не отзывает сохранённые снимки.

## Непрерывное поле

Computed V3 с `assignment` принимает один непрозрачный affine encoded-sRGB
вход на всей нормированной области `[0, 1]`; прочие входы постоянны.
`update_declared_field(revision, surfaces, varying_input, from, to)` принимает
обычный schema-ordered `Vec<u8>`, индекс изменяемого входа и два `ProgramRgb8`.
Изменяемый слот `surfaces` не читается как источник: его задаёт направленный
descriptor `from → to`. V1/V2 возвращают `program_update`; нескольких полей,
прозрачных stops и другого пространства интерполяции этот API не представляет.

`field_assessment()` возвращает owned `Option<ProgramFieldAssessment>`:
`input_index`, endpoints, `source_model: "opaque-affine-encoded-srgb8-half-up-v1"`,
`domain: "whole-field"`, `rendering: "unknown"`, `region_count` и `witnesses`.
Каждый `ProgramFieldWitness` содержит рациональные `numerator`/`denominator`
и исходный `nominal` RGB в порядке физических `case_index` Core.
Для текущих `unsatisfied`/`incomplete` metadata сохраняет координаты причины;
для неизвестного текущего контекста и конечных observations возвращается `None`.
Изменение своей копии metadata, последующее обновление или освобождение runtime
не меняют ранее выданный снимок.

`update_declared_field_with(..., accept)` использует тот же синхронный
`ProgramUpdateHost`: `false` и ошибка сохраняют прежнее состояние, а ту же
ревизию можно предложить снова. Callback получает целый модельный снимок до
принятия; поле не превращает `ready` в гарантию фактических пикселей.
Повторный вход в runtime получает `program_busy`. Native unwind даёт
`program_host_protocol` с операцией вызванного update; недекларированное foreign
исключение, преобразованное UniFFI, относится к общему `ProgramUpdateHost.accept`.

## Условие поддержки

Для новой платформы необходимы готовый устанавливаемый пакет, полный публичный
сценарий Program и обязательная проверка реального внешнего потребителя.
Одного сгенерированного файла или успешного теста Rust недостаточно.

Проверка поверхности извлекает операции из реальных WASM/UniFFI экспортов.
Swift сравнивает их с публичными символами собранного пакета, Kotlin проверяет
методы установленного AAR через отражение. Методы авторинга обоих языков
сравниваются с декларациями действующего JS-пакета.
Проверки имеют отрицательные примеры: отсутствующий метод, скрытый экспорт,
неверное число аргументов и пустой результат обнаружения не проходят.

[Общие истории](../../conformance/program-runtime-v1.json) проверяют изменение
фона, отказ и восстановление через каждый подключённый потребитель.
Отдельные проверки покрывают типизированные ошибки, повтор и конфликт ревизий,
сохранение старого head, callback, владение снимками и завершение.
Реестр численных возможностей сравнивается целиком, а не только по checksum.

ABI и установка проверяются на поддерживаемых средах. В Apple-поставке
исполняются macOS и iOS Simulator; сборка для физического iOS-устройства
проверяет компиляцию и линковку, но не заменяет запуск на устройстве.
В Android-поставке исполняется внешний потребитель на минимальном API и среде
с 16-КБ страницами; отдельно запускается приложение после R8. ABI, зависимости
и упаковка проверяются в конечном APK, а не только в собственной библиотеке.
Область Android-запусков и отличие от проверки ARM-сборки задаёт
[контракт поставки](../../bindings/kotlin/README.md).
Тесты выполняются над теми же байтами архива, которые сохраняются для выпуска.

Android CI один раз собирает внешний debug-проект и его R8 release вместе с
тестовыми APK. Обе среды получают одинаковые подписанные файлы: manifest связывает
все выходы сборки с точным Git-деревом и SDK, хеши проверяются перед установкой и
после исполнения. Gradle остаётся в сборке; устройства запускают готовые APK через
[`adb shell am instrument`](https://developer.android.com/studio/test/command-line).
Полный набор завершённых тестов и итог запуска проверяются по instrumentation
protocol. Пустой, пропущенный, повторный, повреждённый или незавершённый результат
не подтверждает проверку.

Перед каждым Android debug/release сценарием CI ждёт регистрации Package Manager
не более 30 секунд по монотонным часам. Завершённый boot и успешный debug-тест
не подтверждают доступность сервиса для release. Ожидание использует read-only
[`service check package`](https://android.googlesource.com/platform/frameworks/native/+/android-6.0.1_r1/cmds/service/service.cpp#102),
доступный также на минимальном API 23. Ошибки ADB, неожиданный ответ и истечение
срока завершают проверку отказом. Очистка приложения, установка и тесты выполняются
один раз; их ошибка сохраняется и не запускает повтор.

Неподдерживаемая возможность должна оставаться явным отказом или отсутствием
заявления о поддержке. Скрывать её за заглушкой, фиксированными токенами или
успехом соседней платформы нельзя.
