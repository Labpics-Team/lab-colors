# Вычисляемое назначение цветов: Program V3

Приложение объявляет допустимые области цветов, авторские опоры, отношения и
обязательные ограничения. Core назначает RGB всей композиции. Значение ID,
имена токенов и визуальный язык принадлежат приложению; отдельного рецепта
для каждой дизайн-системы не требуется.

## Декларация

`ProgramWireBuilderV3` экспортируется из
`@labpics/colors/program-wire/abi-v3.js`. Он наследует методы графа V1 и добавляет:

```ts
computedTarget(id, domain, anchor, maxDelta);
assignment(targetsInPreferenceOrder);
```

`domain` задаёт множество encoded sRGB8 с включёнными границами:

- `{ kind: "box", lower: [r, g, b], upper: [r, g, b] }` — покомпонентный диапазон;
- `{ kind: "gray", lower: g, upper: g }` — значения `[g, g, g]` в диапазоне.

Все каналы — целые числа от 0 до 255; нижняя граница не больше верхней.
`gray` описывает множество, а не роль, тему или иерархию поверхности.
Полный sRGB8 выражается box от `[0, 0, 0]` до `[255, 255, 255]`.

`anchor` — RGB8-опора приложения. Она может лежать вне области, но это не добавляет
её в допустимое множество. `maxDelta` — конечное неотрицательное расстояние в
метрике профиля ниже; его квадрат также должен быть конечным. Нулевой допуск
разрешает только саму опору, если она принадлежит области.

`assignment()` содержит каждый вычисляемый target ровно один раз и задаёт
лексикографический приоритет: отклонение первой цели важнее отклонения второй.
Числовой порядок ID этого предпочтения не задаёт.

V3 требует хотя бы один `computedTarget`; фиксированные цели допустимы.
Смешивание вычисляемого назначения с `finiteTarget`/`selectionRelease` не
поддерживается. Для конечного списка вариантов остаётся V2. Остальные ограничения
графа, ссылок, количества записей и observations сохраняются. Opacity объявляется
существующими paint-узлами и не становится переменной поиска.

## Правило выбора

Сначала Core проверяет всю композицию с авторскими опорами на всех переданных
сценариях. Если опоры принадлежат областям и все обязательные ограничения
выполнены, RGB сохраняются побайтово.

Иначе допустимое множество образуют области, пределы отклонения и все hard
constraints. Report-only ограничения не запрещают результат. Core выбирает
лексикографический минимум расстояний в порядке `assignment()`, а при равенстве
сравнивает RGB tuples в том же порядке. Выбор проверяется совместно: независимая
коррекция каждой цели не заменяет проверку их отношений. Перед выдачей выполняется
свежая проверка фактически encoded композиции и совпадения с выбранной tuple.

Контраст — обязательное условие, а не максимизируемая оценка. Допустимый тёмный
primary не становится серее лишь потому, что серый тоже проходит порог.
Фиксированный светлый цвет остаётся светлым; при несовместимых условиях движок
возвращает явный исход. Приложение само определяет, какие цвета неизменны,
какие могут отклоняться и насколько.

## Пример: опора и ограниченная область

Пример требует сборки пакета с экспортом `program-wire/abi-v3.js`.
[Инициализация и установка](../../packages/colors/README.md#первый-запуск)
описаны в README пакета. После инициализации WASM:

```js
import { compileProgramWire } from "@labpics/colors";
import {
  ProgramWireBuilderV3,
  SURROUND_AVERAGE_V1,
  WCAG22_SC143_TEXT_DEFAULT_V1,
} from "@labpics/colors/program-wire/abi-v3.js";

const bytes = new ProgramWireBuilderV3()
  .computedTarget(21, { kind: "gray", lower: 0, upper: 96 }, [24, 24, 24], 1)
  .assignment([21])
  .surfaceInputPort(31)
  .solidPaint(41, 21)
  .inputSurface(51, 31)
  .sourceOverOccurrence(61, 41, 51, 64, 0.2, SURROUND_AVERAGE_V1)
  .presentationRoot(71, 61)
  .presentationTarget(71, 61)
  .wcag22VisibleUnary(true, 81, 61, WCAG22_SC143_TEXT_DEFAULT_V1)
  .output(91, 41)
  .finish();

const runtime = compileProgramWire(bytes, 1);
try {
  for (const [index, gray] of [255, 128, 0].entries()) {
    const snapshot = runtime.updateObserved(
      BigInt(index + 1),
      new Uint32Array([1]),
      new Uint8Array([gray, gray, gray]),
      1,
    );
    try {
      console.log({
        version: snapshot.snapshotVersion,
        revision: snapshot.revision,
        state: snapshot.state,
        reason: snapshot.reason,
        rgb: snapshot.state === "ready" ? [...snapshot.outputRgb(0)] : null,
      });
    } finally {
      snapshot.free();
    }
  }
} finally {
  runtime.free();
}
```

На белом фоне допустимая опора сохраняется. При изменении фона Core вычисляет цвет
в заданной области. На чёрном фоне вся эта область слишком тёмная для указанного
текстового контраста: результат `unsatisfied`, без подстановки белого за пределами
области. Числа области, опора и допуск выбраны в этом примере приложением;
они не являются настройками движка для текстовых ролей.

## Снимки и применение результата

V3 использует `snapshotVersion === 2` у standalone и attached snapshots.
`revision` содержит текущую committed revision как `bigint`; `reason` равен
`"limit"` только у `incomplete`, иначе `undefined`.

| `state` | Outputs | Значение |
| --- | --- | --- |
| `ready` | Текущая tuple | Выбор завершён, конечная проверка прошла |
| `unsatisfied` | Нет | Полное допустимое множество пусто |
| `incomplete` | Нет | Предел работы достигнут до доказательства результата |
| `waiting`, `stale` | Нет | Пригодного текущего результата нет |

Найденное промежуточное решение не выдаётся как `ready`. `incomplete` не означает
невозможность решения и не является исключением нехватки памяти.
Синхронный профиль работы принадлежит Core; V3 не принимает число посещений
или настройки алгоритма от потребителя.

Ранее полученный immutable ready snapshot сохраняет свои данные, но не
удостоверяет текущий цвет. V3 не копирует historical outputs в новый снимок.
V1/V2 сохраняют `snapshotVersion === 1`, прежние состояния и историческую
семантику outputs; перед применением таких outputs также нужно проверять `state`.

`attachProgramWire` использует существующий атомарный переход:
подготовка → успешная установка или отзыв host → commit → публикация stamp.
После `incomplete` или `unsatisfied` успешно отозванный результат не остаётся
текущим. Если host отклоняет отзыв или установку, update возвращает ошибку,
а прежний committed head сохраняется. Host соблюдает синхронный point-sink
контракт: отказ не оставляет частичного изменения внешней поверхности.

Повтор той же revision с тем же каноническим наблюдением сохраняет исход без
нового поиска. Новая revision запускает обработку нового наблюдения; retry
прежней revision сам по себе не продолжает остановленный поиск.
Attachment по-прежнему устанавливает один terminal point. Совместный выбор
нескольких целей не означает транзакцию нескольких CSS-свойств.

## Ошибки и совместимость

Готовые V3 bytes принимают общие `compileProgramWire` и `attachProgramWire`.
Входы Rust с суффиксом `_v1` остаются строго V1. Байты, поведение, identities
и ошибки V1/V2 сохраняются.

| Код | Причина |
| --- | --- |
| `program_wire` | Неверные bytes, версия или тег |
| `program_compile` | Недопустимый разобранный граф или параметры |
| `program_unsupported` | Распознанное неподдержанное сочетание assignment и finite selection |
| `program_resource_exhausted` | Ресурсы admission или проверяемая cardinality исчерпаны |

`program_unsupported` относится к операциям `compileProgramWire` и
`attachProgramWire`. Старые ошибки observations, host, индексов и lifecycle
остаются действующими. JavaScript builder использует прежние
`PROGRAM_WIRE_INVALID_DECLARATION` и `PROGRAM_WIRE_TOO_MANY_ENTRIES`;
decoder независимо проверяет сырые bytes.

## Численный профиль и идентичность

Расстояние вычисляется преобразованием `oklch_from_hex` в
`[L, C*cos(h), C*sin(h)]` и суммой квадратов разностей в порядке f64-операций
профиля. Допуск сравнивается по квадратам. Это вычислительная метрика данного
профиля, без утверждения истинного вещественного оптимума или универсальной
оценки красоты.

Semantic identity включает граф, policy, области, опоры, нормализованные допуски
и порядок предпочтений. Предел работы в неё не входит. Отдельная execution-profile
identity связывает численную реализацию и неизменяемую конфигурацию исполнения.
Проверки конкретной сборки должны ссылаться на её фактические bytes; одинаковый
profile label не подтверждает равенство двух бинарных артефактов.

Точность Rust `f64::sin_cos` [зависит от платформы и версии](https://doc.rust-lang.org/stable/std/primitive.f64.html#method.sin_cos).
Совпадение исходников и wire само по себе не доказывает побайтовую эквивалентность
пограничных решений WASM и native. Проверка нового бинарного артефакта требуется
отдельно. Snapshot, identity и внешний отчёт проверки не создают полномочие на
применение цвета: его проверяет действующий attachment через owner, stream,
revision, epoch и свежую конечную проверку.
