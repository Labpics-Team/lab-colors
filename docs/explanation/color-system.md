# Связанная цветовая система

Lab Colors связывает авторский цветовой характер с местом применения.
Дизайн-система объявляет источники, отношения и желаемые свойства один раз;
runtime получает текущие поверхности и вычисляет согласованный набор значений.

## Источник, роль и применение

`role(id, anchor)` сохраняет один исходный цвет и настройки его характера.
`role.on(surface)` создаёт применение, у которого есть реальный фон. Два
применения одной роли могут получить разные RGB: текстовая ссылка на тёмной
поверхности и заливка кнопки решают разные задачи, сохраняя общую цветовую опору.

Повторная передача одного `ColorUse` означает именно общий physical paint.
Это полезно для aliases или нескольких одинаковых элементов. Новое `.on()`
означает самостоятельное применение. Библиотека не объединяет эти две ситуации
по совпадению имени или исходного HEX.

Применение также может служить поверхностью: `ink.on(accent.on(panel))` связывает
надпись с вычисленной заливкой. Core решает всю композицию вместе. Заливка не
превращается в терминальный экран только потому, что у неё есть CSS output.

`fixed` закрепляет физический исходник. Остальные роли вычисляются обычным
путём; отдельного переключателя адаптивности нет.

## Правила поверхностей

Клиент задаёт структуру уровней и их тональные кривые. Кривая содержит пары
`[светлота входной поверхности, предпочтительная светлота применения]` в Oklab.
Между точками применяется линейная интерполяция. Значения лежат в `[0, 1]`,
абсциссы строго возрастают от 0 до 1.

У вложенных поверхностей могут быть разные правила от одного входа. Например,
одна кривая заканчивается светло-серым, а следующая белым; на тёмном конце
вторая поверхность может быть светлее первой. Такая декларация задаёт
поведение без таблицы каждого токена для каждой темы.

`tone.from` явно указывает внешний вход системы. Геометрия вложенности
отдельно задаёт фактическую композицию. Поэтому смена клиентской иерархии
не требует нового режима библиотеки.

## Характер и свойства применения

Политика характера работает в Oklch, производном от [Oklab](https://bottosson.github.io/posts/oklab/).
Пакетный вариант сохраняет направление оттенка в окне ±18°, не менее 10%
исходной chroma и не усиливает её без авторского разрешения. Для sRGB8
допускается округление: если цвет с ограниченной chroma при той же светлоте
и направлении оттенка кодируется в ровно тот же RGB, он сохраняется.
Это не произвольный численный допуск. Точная серая роль остаётся нейтральной.
Эти настройки —
открытый изменяемый выбор дизайна: `identity.maxHueDeviation`,
`identity.chroma` и `identity.lightness` заменяют соответствующие границы.
Явная chroma-граница проверяется строго на конечном encoded цвете.
Chroma задаётся в абсолютных координатах Oklch, светлота — в `[0, 1]`.

Так слабый авторский оттенок не превращается в более насыщенный ради меньшей
ошибки светлоты. Правило относится к конечной композиции: source прозрачного
материала может быть насыщеннее, если этого требует компенсация фона.
Эта геометрическая политика сохраняет часть замысла; она не является моделью
Cleanliness. Тональные приближения проходят те же условия, что другие
кандидаты, и сами по себе не гарантируют пригодность округлённого RGB.

Для каждой роли `maxChange` ограничивает расстояние Oklab от исходной опоры.
Тональная кривая меняет предпочтительный результат, сохраняя исходную опору
этого ограничения. Несколько условий пересекаются; предпочтение не может
компенсировать нарушение обязательного условия.

`separation` задаёт диапазон расстояния Oklab между конечным видимым цветом и
его фактическим фоном. Это позволяет описать отделение панели, лёгкую границу
или выраженный акцент. `contrast` отдельно добавляет конкретный критерий
WCAG 2.2. Условия одинаково применимы к вычисляемому и фиксированному цвету.
Декларация цвета не обязана содержать дополнительное условие: сама роль уже
задаёт область допустимого характера и опору предпочтения.

## Адаптация и прозрачность

При opacity 1 Core может менять RGB применения в ответ на контекст. Пиксель
такого применения остаётся полностью непрозрачным.

При opacity меньше 1 Core подбирает исходник с учётом композиции. Характер,
`maxChange` и предпочтение относятся к конечному видимому результату. Например,
для нейтрального прозрачного слоя над цветным фоном может понадобиться цветной
исходник, компенсирующий подложку. Ограничить в такой ситуации source точной
серой осью означало бы потерять нужный результат.

Прежние проверки характера и `maxChange` используют nominal encoded sRGB8
source-over с конечным округлением каждого канала. Совместный Point-профиль
измеряет расстояние до полной опоры через непрерывное наложение того же графа;
выбранные конечные RGB8 отдельно проходят обязательные проверки. Contrast и separation в обычном V3
пути дополнительно учитывают [диапазон точности растровой композиции](material-emission.md).
`opacity` относится к paint, который получает CSS color с alpha;
CSS opacity общей группы вместе с потомками задаёт другую композицию.

При поиске по областям исходников Core сохраняет зависимость видимого цвета
от его собственной подложки. Оба участвуют в проверке WCAG как одна
source-over операция, включая вложенные вычисляемые поверхности. Полностью
прозрачный слой всегда имеет отношение контраста 1:1 к собственной подложке.
Область исключается лишь тогда, когда консервативная Q55-граница исключает
обе полярности. Оставшиеся решения проходят обычную точную проверку WCAG.

## Выбор результата

Обычный `colors().on()` передаёт в Core операцию `compose`. Если у всех
изменяемых применений связанного компонента есть полная цветовая опора,
Core совместно уменьшает потери замысла: сначала расстояния до явно заданных
опор `tone`, затем до остальных опор. В каждой группе сначала уменьшается
наибольшее расстояние в Oklab, затем следующее. Tone меняет только L опоры. Порядок создания
применений, имена и aliases не задают важность этих расстояний.

Каждое применение оценивается на всех различных локальных контекстах и в
профиль входит его наибольшая потеря. Повтор observation из-за добавления
другого входа не увеличивает вес применения.
При доказанном равенстве полного профиля предпочтений выбирается меньшее
изменение физических исходников, также без первенства деклараций. Это
правило распределения потерь; оно не утверждает неухудшение каждого цвета
или научно подтверждённый Cleaner. Пересечение численных интервалов не
считается равенством. Первое пригодное решение может улучшаться дальше,
даже если исходный авторский цвет сам не выполнял обязательные условия.

В обоих совместных режимах повтор одинакового применения не усиливает его
предпочтение количеством записей, если Core доказал взаимозаменяемость.
Core может объединить поисковую переменную только для доказанно
взаимозаменяемых конечных применений: совпадают замысел, материал, контекст
и все собственные условия, а другие отношения или зависимые элементы не
различают их. Каждое применение сохраняет свой выход и отчёт. Разные условия
и связи остаются самостоятельными; совпадение численной ошибки не означает
эквивалентности.

Результат раскрывает режимы компонентов в `frame.selection`. `joint-point-v1`
означает описанный совместный выбор. Если исходные цвета допустимы и Core
доказал, что каждое отклонение от видимой опоры равно нулю либо неизменно при
всех возможных исходниках, компонента достигла непрерывного минимума. Один
лишь перебор RGB8 оставляет `optimality: unfinished`. В смешанной композиции
статус `exact` требует, чтобы каждая компонента достигла минимума своего режима.
При полной симметрии графа один технический представитель не означает
единственность распределения равноценных цветов между применениями.

### Совместный выбор связанных применений

Например, заголовок и подпись на одной подложке сохраняют авторскую тональную
иерархию через `preserveTonalHierarchy` при смене цвета бумаги. Режим
`joint-reference-peers-v1` совместно выбирает применения с implicit-reference
и все связанные с ними применения независимо от порядка объявления ролей.
Связанные физической композицией
применения могут иметь разные подложки, зависимые от других красок. Прозрачность
сохраняется, видимый цвет вычисляется после всех вложенных наложений.
Если авторские подложки одинаковы, а фактические различаются, Core учитывает
наблюдаемые цвета при распределении бюджета поиска. В нескольких сценариях
он сохраняет сочетания подложек, которые действительно встречаются вместе.

Среди композиций, удовлетворяющих всем обязательным условиям, Core сначала
сравнивает расстояния до явно заданных опор `tone`. Производное из reference
предпочтение соседнего применения не может вытеснить такую опору, если
найдена композиция, лучше сохраняющая её при тех же обязательных условиях.
Далее Core сравнивает недостижимую по физике долю авторского контраста на
выбранной стороне каждой подложки. Границы RGB исходника и его прозрачность
задают самый светлый и самый тёмный возможные видимые цвета. Когда на выбранной
стороне исходный контраст физически возможен, эта потеря равна нулю. Другие
условия могут дополнительно ограничивать выбор. Затем сравниваются расстояния
в Oklab от видимых цветов до виртуальных опор implicit-reference и обычных
цветовых опор. При равенстве
сравниваются изменения физических исходников в Oklab. На каждой ступени
движок сначала уменьшает наибольшую потерю, затем следующую. Явная `tone`
задаёт предпочтительную светлоту этого применения; две ступени implicit-reference
к нему не применяются.

Полная проверка исполняется для целого набора красок. Общие входы учитываются
один раз на каждый различимый локальный контекст, для каждого применения важен
худший из них. `capacity` в этом режиме равна `null`. Полностью симметричные
решения могут различаться распределением равноценных красок. При исчерпании
поиска найденный пригодный результат имеет `state: "ready"` и
`optimality: "unfinished"`. Если пригодный набор ещё не найден, результат —
`unresolved`.

Для каждой рассматриваемой композиции виртуальные опоры и физические пределы
вычисляются на её фактических подложках. Поиск отсекает область только по нижним
границам всех четырёх ступеней сравнения, включая изменение зависимых подложек.
Область поиска охватывает исходники всех связанных красок одновременно.
Ограничения проверяются на границах возможных видимых цветов. Например, если
слабый текст обязан удовлетворять WCAG 2.2 и сохранять тональную иерархию,
его минимальный контраст сужает допустимые области обеих полярностей всей
иерархии. Это условие выводится из ограничений одного применения и его общей
подложки; оно не зависит от имён ролей или конкретной темы. При переводе
доказанных Q55-границ яркости в координаты поиска округление наружу сохраняет
все допустимые варианты. Итоговый набор по-прежнему проверяется точными
проверками всех обязательных условий.
Одиночное implicit-reference применение использует те же критерии выбора.
В обоих совместных режимах расстояния Point, явной `tone` и изменения
исходника вычисляются одним непрерывным интерпретатором с доказательными
интервалами. Только физическая сила implicit-reference и расстояние до его
виртуальной опоры используют операционную модель номинального sRGB8-наложения.
Поэтому добавление связи не меняет математическое значение уже объявленной
опоры. При конечном бюджете поиска пригодные незавершённые результаты
разных задач всё ещё могут различаться.

Если численная оценка полного допустимого набора недоступна, Core сохраняет
его для выдачи пригодного результата и продолжает поиск. Набор с доказательным
интервалом оценки может заменить такой резервный результат. Неудачное
уточнение интервала сохраняет уже полученную корректную границу.
Пересекающиеся интервалы сами по себе не доказывают равенство или преимущество.
Неустановленный порядок и незавершённый обход областей учитываются отдельно;
завершение обхода sRGB8 само по себе не доказывает непрерывный оптимум.

### Явный порядок и совместимость reference

Низкоуровневый `assignment(order)` сохраняет прежний явно объявленный порядок
(`ordered-v1`). В `ordered-reference-v1` порядок применений сохраняется для
совместимости с предыдущим reference-поведением.

Core проверяет всю систему и минимизирует расстояния до предпочтительных
видимых опор в порядке объявления применений. Поверхность создаётся раньше
связанного с ней содержимого. Экспорт одного или нескольких CSS-имён,
добавление alias и перестановка outputs этот приоритет не меняют. Это
последовательный приоритет без скрытой суммы весов. При нескольких физических сценариях для каждого
применения сравнивается наибольшее расстояние среди них. При полном равенстве
видимой оценки Core предпочитает сохранить исходные source-значения в том же
порядке применений, затем использует порядок RGB для оставшейся ничьей.
Прозрачность и округление могут давать один видимый результат из разных
исходников; такое совпадение не требует произвольной коррекции исходного цвета.

В совместимом низкоуровневом режиме `ordered-reference-v1` результат зависит от порядка деклараций.
Перестановка двух связанных применений может изменить распределение потерь
их цветового характера, даже если физическая композиция и условия прежние.
Создание подложки раньше содержимого выражает зависимость, но само по себе
не означает, что замысел подложки важнее. Устранение этого неявного приоритета
требует явного правила совместного выбора в Core: сортировка имён, ID или графа
не определяет, как разрешать конфликт предпочтений. Низкоуровневый `assignment(order)`
сохраняет отдельный смысл явно объявленного автором приоритета.

Связи между вычисляемыми применениями задают совместные обязательные условия
и зависимости видимых предпочтений. Core подбирает каждую независимую группу
отдельно. Явно упорядоченная операция сохраняет порядок объявлений внутри группы. Поэтому добавление отдельного
элемента с тем же фоном не меняет уже найденный цвет. Два независимых применения
одной роли в одинаковых условиях получают одинаковый результат.

Прозрачный слой зависит от изменяемой подложки. Непрозрачная панель прерывает
эту видимую зависимость; явно заданные условия панели относительно внешнего
фона по-прежнему связывают их. Общий неизменяемый вход сам по себе не связывает
поиск независимых применений. Группы объединяются в один полный набор,
который проходит общую проверку перед публикацией.

Вычисляемая поверхность связывает поиск своих дочерних применений, пока её
цвет ещё выбирается. Когда уже найден пригодный полный набор, Core может
предложить первому по приоритету применению его точную видимую опору, если оно
непрозрачно: нулевая дистанция минимальна, а исходный RGB однозначен. Эта опора
должна совпадать во всех физических сценариях и сохранять авторские условия.
После этого оставшиеся зависимости снова разделяются на независимые группы.
Так добавление второго одинакового применения на уже выбранной поверхности
не меняет локальную задачу первого. Прозрачные источники с одинаковым видимым
результатом не получают такого доказательства однозначности. Предложение сохраняется только
при пригодности целого набора. Незавершённая условная попытка
сохраняет полный исходный поиск; её промежуточные изменения принимаются только
после проверки целой композиции.

Если раннее разделение не применялось, в конце поиска Core может отдельно
подобрать первое применение по его собственному контексту и всем условиям,
которые не зависят от оставшихся изменяемых цветов. Например, светлая опора
полупрозрачной поверхности над чёрным фоном может быть недостижима; её лучший
допустимый вариант всё равно не должен теряться из-за повторного поиска
одинакового содержимого. Затем оставшиеся группы ищутся при предложенном
источнике поверхности. Если сам контекст первого применения зависит от них,
самостоятельная задача для него не создаётся и используется уже выбранный
источник. Изменение принимается только после проверки и сравнения полной
композиции по общему приоритету. Локальный выбор среди равных вариантов не
получает приоритета над видимым качеством дочерних применений и не доказывает
точный оптимум всей композиции. Раннее разделение и поздняя доработка вместе
выполняют не более одного прохода поисков условных групп.

Контекстные тональные приближения помогают быстро получить пригодный набор.
Каждая исходная точка сначала приспосабливает менее приоритетные применения,
затем пробует изменения в прямом порядке. Так содержимое получает возможность
адаптироваться к поверхности до изменения самой поверхности. Этот порядок
подготовки кандидатов не меняет обязательных условий и приоритета выбора.
После них остаётся доступным полный заявленный RGB8 domain. Отсечение области
использует границы физической композиции, условий и предпочтения. Перед
возвратом итоговый набор снова проходит физическую проверку.

Часть того же ограниченного объёма поиска улучшает уже пригодную композицию:
возвращает предпочтительный источник, при необходимости приспосабливая связанные
менее приоритетные применения. Проверяется полный набор; непригодное промежуточное
состояние не публикуется. Разные обязательные условия дочерних элементов
сохраняют возможность выбрать разные цвета для применений одной роли.

Готовое решение имеет `optimality: "exact"` или `"unfinished"`. Оба состояния
выполняют обязательные условия. Второе означает, что поиск мог бы ещё улучшить
предпочтение. `conflict` означает полностью исследованную несовместимость,
`unresolved` — отсутствие найденного решения в выполненном объёме поиска.
Диагностика нарушений указывает проверенный кандидат и конкретные условия.

## Обновление интерфейса

`attach` владеет CSS variables входных поверхностей и outputs на выбранном
элементе. `view.set` сначала вычисляет новый полный набор, затем одним изменением
принимает все variables. Отклонённый контекст сохраняет прежний фон и цвета.

Повторный контекст с теми же физическими входами использует уже выбранный
набор. Для нового обновления заново проверяются конечные применения и
формируется новый результат; повторять поиск неизменившегося набора не нужно.
Статус завершённости исходного поиска сохраняется.

Для изменения исходников или политики создаётся новый immutable Program;
`view.replace` передаёт ему тот же элемент после успешной подготовки целого
состояния. Сохранённые снимки результата остаются независимыми.

`program.resolve` принимает уже заданные приложением данные контекста.
`unknown` и `stale` отличают недостающие текущие данные от пригодного результата.
Подробности общего механизма — в [контракте транзакции](../contracts/program-transaction.md).
