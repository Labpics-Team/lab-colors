# Диагностика отказа Program V3

`snapshot.diagnostics()` возвращает данные текущего `unsatisfied` или
`incomplete` результата. Для `ready`, `waiting` и `stale` возвращается `null`.
Свежие output-значения в отказе отсутствуют; диагностический tuple не является
результатом для отображения.

```ts
const diagnostics = snapshot.diagnostics();
// { searchVisited: bigint, searchBudget: bigint, witness: ... | null }
```

`searchVisited` считает посещения объявленного алгоритма поиска, включая
регионы. Это не количество вызовов evaluator или проверенных полных tuple.
`searchBudget` — предел того же алгоритма. `incomplete` отдельно сообщает
`reason === "limit"`: допустимый полный результат ещё не найден. Если поиск
остановлен до первой проверки вычисляемого кандидата, его witness равен `null`.

В computed V3 отдельный поиск получает предел `B = 65 536` посещений.
Независимые группы вычисляемых целей не делят этот предел друг с другом.
В режиме reference appearance поиск набора цветов и оценка достижимости
разделяют один `B` для связанной группы. Если достижимость осталась неизвестной,
допустимый результат имеет `optimality: "unfinished"`; отчёт сохраняет её границы.
Следующее увеличение бюджета для условных поисков относится к прежнему режиму
без reference appearance.
У контекстной группы из `n > 1` целей общая верхняя граница — `(n + 1) × B`: из уже
пригодного набора может быть предложена точная опора первой по приоритету цели,
если её RGB непосредственно задаёт видимый цвет. Когда опора одинакова во всех
сценариях и сохраняет авторские условия,
она задаёт однозначный source с нулевой видимой дистанцией. Затем выполняется
не более `n − 1` условно независимых поисков для остальных целей.
Если ранний поиск условных групп не запускался, в конце первая цель может
получить отдельный поиск с пределом `B` по собственному контексту и hard factors,
не зависящим от оставшихся целей. Только эти факторы задают её локальные входы
и сценарии. Затем единственный проход условных групп проверяет предложение в
композиции, включая alpha. Если первый objective зависит от ещё изменяемого
контекста, используется уже выбранный источник без отдельного поиска первой
цели. Этот поздний путь не объявляет общую оптимизацию завершённой.
Оставшийся один `B` покрывает первоначальную подготовку, проверки условной
попытки и полный исходный поиск при её незавершённости или непригодности.
Пригодные результаты условных групп объединяются и при незавершённой
оптимизации одной из них; это не даёт права объявить весь выбор точным.
Проход условных поисков одноуровневый; рекурсивного умножения бюджета нет. После
появления пригодного набора в исходном `B` резервируется посещение для полной
проверки поздней доработки. Если первое пригодное решение найдено на последнем
посещении, оно сохраняется без неоплаченной дополнительной проверки.
Для одиночной контекстной цели и computed-группы без контекстного color intent
верхняя граница остаётся `B`.

`searchVisited` суммирует фактически выполненную работу, включая условные
поиски и продолженный исходный поиск. `searchBudget` суммирует верхние границы
групп и отдельную проверку условий, зависящих только от фиксированных значений.
Фактический поиск может закончиться существенно раньше. Готовый результат
всё равно проходит общую физическую проверку целого набора.

Условия, зависящие только от изначально фиксированных значений, проверяются один раз даже
при нулевом бюджете вычисляемых целей. Их нарушение уже устанавливает конфликт
целого набора и может иметь witness. Если они выполнены, нулевой бюджет поиска
остаётся `incomplete` без witness вычисляемого кандидата.

## Свидетельство конкретного attempt

Непустой `witness` имеет `kind: "authored-tuple"`. Core повторно проверяет
исходные authored RGB всех изменяемых target на актуальном полном наборе
физических cases. Эта диагностическая проверка ранее отвергнутого tuple не
продолжает поиск и не меняет его счётчики.

- `targets` содержит `{ targetId, source }` диагностического tuple.
- `caseScenarioIds[caseIndex]` содержит исходные scenario ID, физически
  схлопнутые в этот case.
- `violations` содержит типизированные нарушения именно этого tuple.

| `kind` | Поля | Значение |
| --- | --- | --- |
| `hard-constraint` | `constraintId`, `caseIndex`, `subject` | Нарушено конкретное объявленное hard-условие. Клиент сопоставляет ID своей декларации. |
| `target-domain` | `targetId`, `source` | Авторский source лежит вне объявленного множества RGB. |
| `color-identity` | `targetId`, `caseIndex`, `occurrenceId`, `actual` | Фактический цвет вне объявленной области характера цвета. |
| `max-change` | те же поля, `distanceSquared`, `maximumDistance` | Превышен hard-допуск изменения относительно authored anchor. Сравнение Core использует squared distance и квадрат допуска. |
| `tonal-hierarchy` | `constraintId`, `caseIndex`, `strongerOccurrenceId`, `weakerOccurrenceId`, `requiredRatio`, `actualRatio`, `requiredGap`, `actualGap`, `strongerPolarity`, `weakerPolarity` | Нарушено отношение исходной силы либо общая ненулевая сторона фона. Ratio — `CRstrong/CRweak`; gap — его натуральный логарифм только для диагностики. |

Для `color-identity` и `max-change` непустой `occurrenceId` означает измерение
финального visible в указанном применении. При `null` оценено intrinsic значение.
В reference appearance идентичность относится к source, поэтому у её нарушения
`occurrenceId` равен `null`. `max-change` сравнивает конечный visible с исходным
visible в reference composition и сохраняет ID применения.
`subject` различает target, occurrence, reference intrinsic/visible relation и
point presentation; relation reference не выдаётся за полный состав отношения.

Witness не является минимальным несовместимым набором условий и не доказывает,
что именно эти нарушения имеют все остальные кандидаты. Полнота отказа
определяется отдельно состоянием `unsatisfied`; при `incomplete` область ещё
не исчерпана. Core не подменяет это различие непрозрачной строкой `failed`.

## Владение и транзакция

Снимок владеет независимой копией диагностических данных. Последующие updates
не меняют ранее полученный witness. Все Rust-буферы копируются с проверкой
выделения памяти до принятия подготовленного перехода. Отказ host callback
сохраняет предыдущую ревизию и её цвета; вычисленный кандидат с diagnostics
можно изучить без принятия новой наблюдаемой композиции.

JS-проекция рекурсивно замораживает свои объекты и массивы. Она не вычисляет
новых оценок, не меняет решение и не выдаёт право публикации output.
